# 现有 MVP 可信化规格

状态：方案审核通过；本地实现待独立代码审核
变更标识：`stabilize-current-mvp`
适用仓库：`/Users/mentianlu/Code/travel`

## 1. 背景与问题

现有 MVP 已能创建旅行项目、异步采集候选、生成报告、分享页面并投票，但当前实现仍把数据库整数项目 ID 暴露给浏览器，创建者凭证出现在 URL/header，项目读取与投票缺少完整的分享令牌边界，也没有可验证的限流、预算、候选身份、重采集幂等、删除恢复、CI 和浏览器端验收链路。

历史任务勾选、Compose 配置和旧截图不构成当前完成证据。2026-08-08 的只读检查显示公共域名 `travel.umafans.run` 为 NXDOMAIN；因此线上状态为“不可公开访问，服务器内部状态未知”，不得猜测线上成功。

## 2. 目标

1. 建立分享访问、创建者管理和匿名投票彼此分离的最小安全边界。
2. 为项目创建、重采集、投票和外部数据调用建立可验证的滥用与成本上限。
3. 使重采集并发安全、可恢复、不会重复记账或无限追加候选。
4. 建立保守的候选来源身份、生命周期、去重、人工覆盖与审计规则。
5. 补齐可信化所必需的创建者 UI、投票可见性、导出和降级说明。
6. 建立从空数据库迁移、后端测试、前端生产构建、Compose smoke 和浏览器 E2E 的自动化证据。
7. 在获得单独发布授权后恢复公开域名，并以可重复的线上 smoke 证明项目一完成。

## 3. 非目标

- 不新增采集来源、行程排程引擎、旅行段、Plan B、完整预算模型或预约管理。
- 不建设交互地图、KML 导出、账号体系、多创建者协作或完整数据治理后台。
- 不重做报告信息架构和全站视觉系统。
- 不引入新的付费错误追踪 SaaS；本项目只要求结构化、脱敏日志与健康检查。
- 不把生产部署、DNS、迁移或其他生产写入视为当前“开始吧”的授权。

## 4. 用户角色与权限

### 4.1 分享访问者

- 只有持当前有效分享令牌者才能读取项目、状态、报告、SSE、候选和公开导出，或对该项目候选投票。
- 轮换分享令牌后，旧令牌立即失效。
- 默认只看到自己的投票；创建者公开汇总后才能看到匿名总数。

### 4.2 创建者

- 创建项目后由服务端设置限定项目 API 路径的 `HttpOnly`、`Secure`、`SameSite` Cookie；浏览器 URL、JavaScript 存储和响应正文均不保存创建者凭证。
- 创建时展示一次离线恢复密钥；服务端只保存其哈希。
- 恢复操作签发新创建者 Cookie，并立即使旧创建者凭证失效。
- 创建者可以轮换分享链接、删除/恢复项目、重采集、管理手工地点、编辑候选覆盖值、审核疑似重复、公开/隐藏票数，并获得私有导出。

### 4.3 匿名投票者

- 服务端设置 `HttpOnly` 投票者 Cookie；同一投票者对同一候选只有一个当前有效投票，改变选择执行 upsert。
- 投票者标识不得在 API 响应、导出、页面或日志中暴露。

## 5. 功能需求

### FR-01 分享令牌与路由

- 删除所有浏览器可调用的数字项目 ID API；数据库整数项目 ID 仅作内部外键，且不得出现在 project/status/report/SSE/export/错误等浏览器响应中。
- 所有项目范围 API 统一嵌套在分享令牌下，并在访问候选时验证其确属该项目。
- 不存在、已轮换、已删除或已清除的分享令牌统一返回不泄露状态的 404。

### FR-02 创建者凭证与恢复

- 创建者 Cookie 只发送到对应项目管理 API 路径，固定有效期 180 天且不滑动续期；过期后必须使用恢复密钥签发新凭证。
- 恢复密钥至少具备 128 bit 熵，只展示一次，支持复制/下载提示；日志和遥测不得记录原文。
- 旧版 `creator_token` 曾被产品放入分享链接，因此它不能作为所有权证明，也不得自动兑换创建者 Cookie 或恢复密钥。没有独立恢复密钥的旧项目进入 `legacy_unclaimed`：分享读取继续可用，创建者写操作 fail closed；只有具备分享链接之外额外所有权证据的人工认领流程才能恢复管理，否则创建新项目。

### FR-03 项目生命周期

- 未主动删除的项目长期保留。
- 创建者删除后立即禁止分享读取和管理，保留 30 天恢复窗口；恢复后原项目数据恢复可用并轮换分享令牌。
- 30 天后由后台任务级联物理清除业务数据。备份和安全日志的独立保留期限必须在用户文档中披露。
- 删除或分享令牌轮换必须立即终止旧 SSE；删除还必须 fence 活动 run/outbox/租约，后续任何外部调用或数据写入均不得继续。

### FR-04 创建与重采集限制

- 项目创建按可信客户端 IP 限制为每小时 3 次、滚动 24 小时 10 次，检查必须发生在项目、run 或任务写入之前。
- IPv6 按 `/64` 规范化；只有配置的可信反向代理可以提供转发地址。
- 重采集每项目冷却 1 小时，滚动 24 小时最多 6 次。
- 当项目已有 `pending/running/generating` run 时，重复请求返回同一个活动 run，不新建 run、不重复记预算、不重复派发任务。

### FR-05 投票限制与可见性

- 投票需有效分享令牌。
- 每项目+IP 最多 60 次/10 分钟及 300 次/滚动 24 小时；同一投票者+候选最多改变 10 次/滚动 24 小时。
- 默认隐藏汇总，普通访问者只收到自己的投票；创建者可以公开并再次隐藏汇总。再次隐藏只影响未来响应。
- 任何模式下均不返回投票者身份。公开导出遵循隐藏状态；创建者私有导出可包含匿名汇总。

### FR-06 候选容量和外部预算

- 每项目最多 300 个活动 canonical 候选，其中自动来源最多 250 个，保留至少 50 个手工候选容量。
- 每次采集最多预留 150 个外部请求；项目生命周期最多 500 个外部请求和估算付费成本 USD 2。
- 单一 provider 每批最多 40 个、生命周期最多 150 个请求，同时不得超过项目请求预算的 40% 或估算付费成本的 50%。
- 预算预留必须发生在外部调用前。触顶时停止新调用，保留成功/缓存/手工数据，run 标记为部分完成并展示覆盖不完整；生命周期预算耗尽时阻止未来重采集。

### FR-07 候选身份与来源生命周期

- 来源身份键为 `identity_provider + entity_type + external_id`；collector vendor/version 只作来源证据，不进入身份键；手工候选使用内部 UUID。
- 无 external ID 时优先使用同 provider 的 canonical URL；否则使用 `provider + entity_type + 规范化名称 + 完整地址` 的确定性 fingerprint。
- 证据不足的来源记录标为 `provisional`，不得按名称/城市模糊自动合并。
- 仅完整、成功且未因预算截断的 provider run 才能累计“未出现”；连续 3 次且跨度至少 7 天后，该来源转 inactive。
- 仅当全部自动来源 inactive 且候选不是纯手工创建时，canonical 候选才 inactive；历史、投票和手工覆盖保留。

### FR-08 去重、合并与人工审核

- 新来源记录置信度 `>= 0.98` 才可自动关联；`0.85–0.98` 生成审核建议；`< 0.85` 保持分开。
- 跨 provider 只有“相同电话或官方域名”，或“距离不超过 50m + 高名称相似 + 类型兼容 + 无地区冲突”的强组合信号可自动关联。
- 已有投票或手工覆盖的 canonical 候选，除同 provider+类型+external ID 完全一致外，必须人工确认。
- 历史数据只对同 provider+类型+external ID 自动合并；其他只生成 dry-run 建议。
- 创建者审核界面显示关键证据并允许“合并”或“保持分开”；决定持久化并阻止重复建议。
- 合并在单事务内完成。相同投票者冲突保留 `updated_at` 最新值，旧冲突进入只读合并审计，随后重算汇总；任一步失败整体回滚。

### FR-09 手工候选、覆盖与审计

- 创建者可用轻量编辑器添加候选：名称、类别必填；区域、来源链接、备注、建议档位可选，创建后可编辑。
- 自动数据保存为系统值；`name/category/area/source_url/notes/tier/summary` 的人工编辑保存为可清空的字段级覆盖值。清空覆盖即恢复对应系统值；`notes` 没有系统值，清空后为空。纯手工候选的初始值作为 manual base，后续变更同样版本化和审计。
- 每次人工变更记录时间、字段、前后值与创建者角色；创建者可以恢复单个旧值，恢复动作自身继续留痕。
- 纯手工候选永不因自动来源缺失而失活。

### FR-10 降级状态与导出

- 所有访问者能看到：覆盖是否完整、数据更新时间、缺失的用户可理解类别。
- 创建者额外看到：各来源脱敏状态、预算使用量、阻断原因和建议动作。
- 原始 provider 错误、密钥、内部 URL、堆栈和数据库信息不得暴露。
- Google Maps JSON 导出保留；无需新增 KML。导出包含最新有效 tier；投票汇总遵循 FR-05。

### FR-11 可重复验证与线上完成

- CI 必须运行后端 lint/测试、迁移新建库 upgrade 与 downgrade/upgrade、前端 typecheck/生产 build、provider mock 合约、Compose smoke 和关键浏览器 E2E。
- 测试和 CI 不允许访问真实付费 provider。
- 健康检查只报告组件状态，不返回异常原文。
- 项目一只有在本地实现通过独立代码审核、用户另行明确授权发布、生产迁移与部署成功、DNS/TLS/页面/API/投票 smoke 可重复通过后才标记完成。

## 6. 用户可观察行为

1. 新建项目后，URL 仅含分享令牌；页面提示保存一次性恢复密钥。
2. 未持分享令牌者无法枚举或读取任何项目资源。
3. 重复点击重采集只显示同一个进行中任务，冷却或预算不足时显示明确原因。
4. 采集不完整时页面保留已有数据并明确标注覆盖缺口。
5. 普通访问者默认看不到他人票数；创建者可公开/隐藏。
6. 创建者能添加/编辑手工地点、恢复字段历史、处理重复建议和导出私有汇总。
7. 删除项目后链接立即不可用；30 天内用恢复密钥恢复后获得新分享链接。

## 7. 验收标准

- **AC-01**：所有旧数字项目路由不可用；每个项目范围 API 都拒绝无效分享令牌和跨项目候选访问。
- **AC-02**：创建者原始凭证不出现在 URL、JS 存储、响应或日志；恢复和经独立证据批准的人工认领会轮换凭证；旧 creator 链接只清除 query，不授予或兑换任何权限。
- **AC-03**：删除、30 天恢复和超期清除的状态转换及权限符合 FR-03。
- **AC-04**：创建、重采集、投票的所有时间窗和并发边界有确定性测试。
- **AC-05**：外部请求在调用前原子预留，任何 provider/批次/生命周期/成本上限均不能被并发或重试突破。
- **AC-06**：候选身份、provisional、缺失失活、手工保护、阈值分层和合并事务有正常/边界/回归测试。
- **AC-07**：访客/创建者投票可见性、匿名性和公开/私有导出符合 FR-05/FR-10。
- **AC-08**：轻量手工编辑、字段覆盖、审计、单字段恢复和重复审核队列可通过浏览器完成。
- **AC-09**：从空库及带旧数据的既有 schema 都可安全迁移；失败步骤可停止并按 rollout 回退。
- **AC-10**：CI 所有门禁在无真实 provider 网络时通过；健康检查不泄露内部异常。
- **AC-11**：获得明确发布授权后，公开域名的 DNS、TLS、首页、创建、分享读取、Cookie 投票及创建者操作 smoke 均有当前证据。

## 8. 已确认决策、假设与未决事项

产品决策已由用户逐项确认并冻结，均体现在 FR-01 至 FR-11。技术假设如下：

- 延续现有 Next.js 14、FastAPI、SQLAlchemy、PostgreSQL、Celery、Redis 和 Docker Compose；本项目不更换平台。
- 生产代理必须能配置可信代理网段并把 API 与前端置于满足 Secure/SameSite Cookie 的同站点拓扑。
- 生产数据库实际 revision、数据量、备份能力、主机和 DNS 权限在发布前仍为 unknown，必须只读重查。

当前没有待用户决定的产品事项。任何扩大产品范围、改变保留/预算/权限语义或执行生产写入的要求都必须重新取得用户决定或发布授权。
